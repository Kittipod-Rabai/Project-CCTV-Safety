# Project CCTV Safety — บทพูดและแนวทางสาธิต

วันที่จัดเตรียม: 14 ตุลาคม 2026

ใช้คู่กับ [เนื้อหาสไลด์](slides.md) และ [หลักฐาน](evidence.md) สถานะล่าสุดอ้างอิง [งาน 1](pipeline-live-verification.md) และ [งาน 2](history-verification.md) รวม [งาน 3 Dashboard](dashboard-verification.md) และ [งาน 4 แจ้งเหตุสงสัย](notifications-verification.md) รวม [งาน 5 ค่าตั้ง](settings-verification.md) บทพูดนี้เป็นร่างสำหรับซ้อม สามารถปรับสรรพนามและคำลงท้ายให้เหมาะกับผู้พูดได้

เวลาพูดและเดโม 14 นาที + เวลาสำรองเปลี่ยนหน้าจอ/รอผล 1 นาที = 15 นาที ไม่รวมถาม–ตอบ เวลาแต่ละสไลด์เป็นเพดานสำหรับการอธิบายรวมภาพประกอบ ไม่ใช่เวลาที่ได้จากการอ่านบทพูดนี้เพียงอย่างเดียว

## สไลด์ 01 — ชื่อโครงการและสมาชิก | 00:30

“สวัสดีค่ะ วันนี้จะนำเสนอสรุปผลการดำเนินงาน Project CCTV Safety ซึ่งเป็นระบบต้นแบบสำหรับวิเคราะห์ภาพและวิดีโอ เพื่อช่วยตรวจจับเหตุด้านความปลอดภัย โดยจะเล่าตั้งแต่การเตรียมข้อมูล การพัฒนาโมเดล ผลการทดลอง และสาธิตผลงานที่ทำได้จริงค่ะ”

`[ต้องเติมข้อมูล: แนะนำสมาชิกและหน้าที่หลักแบบสั้น ๆ]`

เชื่อมสไลด์: “เริ่มจากปัญหาที่ทำให้ทีมเลือกทำโครงการนี้ค่ะ”

## สไลด์ 02 — ที่มาและปัญหาที่ต้องการแก้ | 01:00

“การมีกล้อง CCTV ช่วยให้เรามีภาพเหตุการณ์ แต่การตรวจดูภาพยังต้องอาศัยเจ้าหน้าที่ โดยเฉพาะเมื่อมีภาพต่อเนื่องและมีเหตุหลายประเภท ทีมจึงศึกษาว่า AI จะช่วยวิเคราะห์ข้อมูลภาพและวิดีโอ เพื่อเป็นข้อมูลประกอบการตรวจสอบได้อย่างไรค่ะ”

“เหตุบางประเภท เช่น ไฟหรือหมวกนิรภัย สามารถเริ่มวิเคราะห์จากภาพแต่ละเฟรมได้ แต่การต่อสู้ต้องดูการเคลื่อนไหวต่อเนื่องด้วย ความแตกต่างนี้เป็นเหตุผลที่เราแยกการวิเคราะห์ออกเป็นสองส่วนค่ะ”

ชี้ภาพตัวอย่างเพื่ออธิบายความแตกต่าง ไม่อ้างว่าทดสอบการลดภาระเจ้าหน้าที่แล้ว

เชื่อมสไลด์: “จากปัญหานี้ เราจึงกำหนดวัตถุประสงค์และขอบเขตการทดลองดังนี้ค่ะ”

## สไลด์ 03 — วัตถุประสงค์และขอบเขต | 01:00

“งานที่นำเสนอมีสามส่วนหลัก คือ โมเดลตรวจจับหกคลาส โมเดลจำแนกการต่อสู้จากวิดีโอ และเว็บต้นแบบสำหรับรับไฟล์และแสดงผลค่ะ ขอบเขตการประเมินครั้งนี้ใช้ชุดข้อมูลสาธารณะและเป็นการทดลองระดับ pilot จึงยังไม่ได้สรุปว่าระบบพร้อมใช้กับกล้องทุกสภาพแวดล้อมค่ะ”

`[ต้องเติมข้อมูล: ปรับบทพูดให้ตรงกับวัตถุประสงค์ฉบับส่งอาจารย์ โดยไม่ตัดเป้าหมายที่ยังไม่สำเร็จออก]`

เชื่อมสไลด์: “ต่อไปเป็นภาพรวมว่าแต่ละส่วนเชื่อมกันอย่างไรค่ะ”

## สไลด์ 04 — สถาปัตยกรรม | 01:30

“ผู้ใช้ส่งภาพหรือวิดีโอจากหน้าเว็บไปยัง FastAPI จากนั้น Stage 1 ใช้ YOLO ตรวจจับคน หมวก เสื้อกั๊ก การล้ม ไฟ และควัน พร้อมตำแหน่งและ confidence ค่ะ สำหรับ PPE เรานำตำแหน่งหมวกและเสื้อกั๊กไปเทียบกับบริเวณของคน เพื่อประเมินว่าตรวจพบอุปกรณ์หรือไม่”

“ส่วน Fight เราใช้ X3D-S วิเคราะห์ลำดับเฟรม เพราะข้อมูลการเคลื่อนไหวช่วยแยกเหตุการณ์ได้มากกว่าการดูภาพเดียว ผลที่ได้เป็น Fight หรือ Non-fight ของช่วงวิดีโอ ไม่ใช่ bounding box ของคลาส Fight ค่ะ”

“ใน pipeline รวม เรายังให้ X3D วิเคราะห์ทุกช่วง เพื่อเปรียบเทียบกับสัญญาณ candidate จากการติดตามคน ส่วนนี้เรียกว่า shadow mode และยังไม่ได้เป็นระบบแจ้งเตือนครบวงจร ผลโมเดลบันทึกใน SQLite เพื่อเปิดดูและเปลี่ยนสถานะตรวจสอบจากหน้า Alert / Logs ได้ ภาพที่นำไปแสดงผลมีส่วนตรวจจับและเบลอใบหน้าด้วย YuNet ค่ะ”

ชี้แผนภาพตามเส้นทางรับไฟล์ → โมเดล → ผลลัพธ์ และแยกภาพแสดงผลออกจากภาพที่ใช้วิเคราะห์

เชื่อมสไลด์: “เมื่อแบ่งหน้าที่ของโมเดลแล้ว ขั้นต่อมาคือเตรียมข้อมูลให้ตรงกับแต่ละงานค่ะ”

## สไลด์ 05 — ชุดข้อมูล | 01:30

“Stage 1 รวมข้อมูลจาก Construction-PPE, D-Fire และ Fall pilot โดย manifest ระบุทั้งหมด 23,169 ภาพ และ 32,639 bounding boxes แบ่งเป็น Train 18,530 ภาพ Validation 1,667 ภาพ และ Test 2,972 ภาพค่ะ”

“ก่อนทดลองมีงานตรวจ label ข้อมูลซ้ำ และความเสี่ยงที่ภาพจากฉากเดียวกันข้ามชุด แต่ชุดข้อมูลยังเป็น provisional และมีข้อจำกัดที่บันทึกไว้ โดยเฉพาะจำนวนข้อมูลแต่ละคลาสไม่เท่ากัน เช่น Fall มีเพียง 141 boxes ค่ะ”

“Stage 2 ใช้ SCFD pilot จำนวน 300 คลิป คลิปละสองวินาที แบ่งเป็น 210 คลิปสำหรับฝึก 45 คลิปสำหรับ validation และ 45 คลิปสำหรับทดสอบค่ะ เราแยกการรายงานข้อมูลภาพกับข้อมูลคลิป เพราะเป็นคนละงานและคนละหน่วยค่ะ”

ชี้ภาพ label จริงหนึ่งภาพ และอธิบายว่าชุดทดสอบใช้ประเมินหลังฝึก ไม่ใช้เลือก checkpoint

เชื่อมสไลด์: “ต่อไปเป็นการตั้งค่าการฝึกและสิ่งที่ได้จากแต่ละโมเดลค่ะ”

## สไลด์ 06 — การฝึกโมเดล | 01:30

“สำหรับ Stage 1 เราทดลอง YOLOv8n เป็น baseline และ YOLOv8s เป็นตัวเปรียบเทียบ โดย arguments ที่เก็บไว้ระบุขนาดภาพ 640, batch 16 และ seed 42 เหมือนกันค่ะ อย่างไรก็ตาม YOLOv8n มีการ resume ส่วน YOLOv8s ฝึกเป็นงานแยก จึงไม่กล่าวว่าเงื่อนไขทุกอย่างเหมือนกันทั้งหมด”

“แม้จะตั้งไว้ 100 epochs แต่ประวัติ YOLOv8n มี 81 epochs และ YOLOv8s จบที่ 86 epochs ด้วย early stopping ส่วน X3D-S จบที่ 9 epochs และเลือก checkpoint ที่ epoch 3 ตาม validation ค่ะ การเตรียมข้อมูลเข้า X3D ใช้ 13 เฟรมและขนาดภาพ 224 คูณ 224”

`[ต้องเติมข้อมูล: เลือกกราฟจาก logs จริง แล้วชี้แนวโน้มที่มองเห็นโดยไม่เดาเหตุผลของการหยุด run]`

เชื่อมสไลด์: “หลังจากได้ checkpoint แล้ว เราประเมินบนชุดทดสอบที่แยกไว้ ได้ผลดังนี้ค่ะ”

## สไลด์ 07 — ผลการทดลอง | 02:00

“ผล Stage 1 ในบันทึกนี้ YOLOv8n ได้ mAP@50 ประมาณ 84.18 เปอร์เซ็นต์ และ YOLOv8s ได้ประมาณ 86.98 เปอร์เซ็นต์ ส่วน mAP@50–95 อยู่ที่ประมาณ 43.77 และ 45.73 เปอร์เซ็นต์ตามลำดับค่ะ ตัวหลังประเมินหลายระดับความทับซ้อนของกรอบ จึงช่วยสะท้อนความเข้มงวดด้านตำแหน่งด้วย”

“YOLOv8s มีค่ารวมสูงกว่าในผลทดลองนี้ แต่การเลือกใช้จริงต้องดูผลแต่ละคลาสและความเร็วบนเครื่องเป้าหมายด้วย เราจึงยังไม่สรุปว่าเป็นตัวเลือกที่ดีที่สุดทุกกรณีค่ะ”

“สำหรับ X3D-S ทดสอบ 45 คลิป ได้ Accuracy 80 เปอร์เซ็นต์ และ Macro-F1 ประมาณ 0.7984 เมื่อดู confusion matrix จะพบว่า Fight ถูกจำแนกถูก 16 จาก 23 คลิป และยังพลาด 7 คลิป จึงมีข้อจำกัดด้านการตรวจพบเหตุที่ต้องปรับปรุงค่ะ”

ชี้ตัวอย่างที่ตรวจถูกและผิดจากไฟล์ที่ทีมตรวจสอบแล้ว `[ต้องเติมข้อมูล: ตัวอย่างและคำอธิบาย]`

“ตัวเลขเหล่านี้เป็นผลของโมเดลบนชุดทดสอบ ยังไม่ใช่อัตราความสำเร็จของระบบแจ้งเตือนทั้งหมดค่ะ”

เชื่อมสไลด์: “ต่อไปจะสาธิตว่าผลโมเดลถูกนำมาแสดงบนเว็บอย่างไรค่ะ”

## สไลด์ 08 — สาธิต | 02:30

### เตรียมก่อนวันนำเสนอ

- เริ่ม backend และเปิดหน้าเว็บไว้ก่อนขึ้นนำเสนอ ตามวิธีใน [README เว็บ](../../mockup/README.md)
- เตรียม local pack หากต้องแสดงหลักฐาน D-Fire และซ้อม [เรื่องหลัก PPE ไม่ครบ 90 วินาที](shared-demo-verification.md); หากจะรันโหมดจริงเพิ่ม ให้ทดสอบและโหลดโมเดลล่วงหน้าแยกจากเดโม
- ตรวจว่า preview ที่ผ่านการตรวจและ checksum พร้อมใช้ ภาพ Smoke เป็น D-Fire ไม่ใช่ภาพโรงงานจริง ส่วนพื้นที่ติดตั้งในเรื่องเป็นบริบทสมมติ
- บันทึกหน้าจอสำรองของเดโมเดียวกัน `[ต้องเติมข้อมูล: ตำแหน่งไฟล์สำรอง]`
- ใช้ [runtime และเวลาที่วัดในงาน 1](pipeline-live-verification.md#runtime-และเวลาใช้งานที่สังเกต) เป็นข้อมูลประกอบ: RTX 4050 Laptop GPU, Pipeline fi008.mp4 บน CPU/YOLOv8n 8.510 วินาที และ CUDA/YOLOv8s 8.540 วินาที เป็นคนละเงื่อนไขและรวม cold load จึงไม่ใช้เทียบความเร็วโดยตรง
- `[ต้องเติมข้อมูล: ผลซ้อมและเวลาประมวลผลบนเครื่องพรีจริง]` เวลาเดิมเป็นหลักฐานของรอบทดสอบ ไม่รับรองเวลาสาธิตครั้งถัดไป

### ลำดับการสาธิต

1. **30 วินาที:** ชี้ว่าโหมดจริงเรียก API/โมเดล และโหมดสาธิตใช้หน้าจอเดียวกันโดยไม่ inference ใหม่ อธิบายป้ายผลบันทึกจริง/สถานการณ์สมมติ
2. **90 วินาที:** เล่นเรื่องหลักตาม [คู่มือ](shared-demo-verification.md): Live ฉาก PPE ไม่ครบ → แจ้งเตือน → Logs → รับทราบ → Dashboard ใช้เล่น/พัก/เหตุการณ์ถัดไปช่วยคุมเวลา
3. **30 วินาที:** ชี้ผล Smoke 0.8779 / Fire 0.3589 จากภาพทดสอบ D-Fire ที่บันทึกไว้ พร้อมย้ำว่าเป็นภาพกลางแจ้งเล่นซ้ำ ไม่ใช่ภาพโรงงานหรือผล inference ใหม่ ส่วนกรณี PPE/Fall/Fight เป็นสถานการณ์สมมติ ไม่ใช่หลักฐานความแม่นยำ

### บทพูดนำ

“เว็บ AEGIVIS มีโหมดจริงที่รับไฟล์แล้วเรียกโมเดล และโหมดสาธิตที่ใช้หน้าจอเดียวกันค่ะ เรื่องหลักเป็นฉากโรงงานสมมติที่แสดงผล PPE ไม่ครบ เพื่อให้เห็นการแจ้งเตือน Logs และ Dashboard เชื่อมกัน คะแนนในฉากนี้กำหนดไว้ ไม่ได้ inference ใหม่ ส่วนผล Smoke/Fire จากภาพทดสอบ D-Fire เป็นหลักฐานที่บันทึกไว้จากภาพกลางแจ้ง ไม่ใช่ภาพโรงงานหรือการรันสดค่ะ”

### เมื่อเดโมมีปัญหา

- หาก error หรือรอนานเกินงบเดโม ให้เปลี่ยนเป็นคลิปสำรอง ไม่แก้ environment ระหว่างนำเสนอ
- แจ้งว่า “ขอใช้บันทึกการสาธิตจากการรันก่อนหน้านี้บนเครื่องที่ทดสอบไว้” ไม่กล่าวว่าเป็นผลสด
- หากโมเดลทำนายผิด ให้อธิบายตามผลจริง ไม่เปลี่ยนไปใช้จอ mock เพื่อแสดงว่าระบบตรวจพบ
- Live ในโหมดสาธิตเป็นตัวเล่นผลตามสถานการณ์ ส่วน Live replay ที่เรียกโมเดลจริงเป็นคนละโหมดและไม่เรียกว่า RTSP สด

เชื่อมสไลด์: “จากโมเดลและเดโม เราสรุปผลเทียบกับวัตถุประสงค์ได้ดังนี้ค่ะ”

## สไลด์ 09 — ผลเทียบวัตถุประสงค์ | 01:00

“ในด้านโมเดลตรวจจับและโมเดล Fight เรามีน้ำหนักและผลทดสอบจริง จึงสรุปว่าสำเร็จในระดับ pilot ค่ะ ด้านเว็บได้ตรวจ Pipeline รวมและ Live replay ทั้ง CPU และ CUDA บนเครื่องทดสอบแล้ว รวมการหยุด เริ่มใหม่ และการคืนทรัพยากร หากเปลี่ยนเครื่องนำเสนอต้องตรวจซ้ำบนเครื่องนั้นค่ะ”

“หากประเมินถึงระบบเฝ้าระวังและแจ้งเตือนครบวงจร งานยังสำเร็จบางส่วน เพราะยังไม่มีระบบแจ้งเตือนครบวงจรและผลประเมินกับกล้องเป้าหมาย แม้ Dashboard ประวัติ SQLite การแจ้งเหตุสงสัย และค่าตั้งที่บันทึกในเครื่องจะทำงานจริงแล้วค่ะ”

`[ต้องเติมข้อมูล: ใช้วัตถุประสงค์เดียวกับฉบับข้อเสนอโครงการ และเติมผลซ้อมเดโมก่อนใช้บทพูดจริง]`

## คำถามที่ควรเตรียมตอบ

### ทำไมใช้สองโมเดล?

YOLO ให้ตำแหน่งสิ่งที่ตรวจพบในแต่ละภาพ ส่วน X3D-S ใช้ข้อมูลต่อเนื่องเพื่อจำแนก Fight / Non-fight ทั้งสองส่วนแก้โจทย์ต่างกัน

### YOLOv8s แม่นกว่า จึงเลือกใช้ได้เลยหรือไม่?

มีค่ารวมสูงกว่าในบันทึกทดลอง แต่ยังต้องพิจารณาผลรายคลาส ความเร็ว และเงื่อนไขการทดลองร่วมกัน จึงมีทั้งสองรุ่นให้ทดลองบนต้นแบบ

### ตัวเลข 86.98% คือความแม่นยำทั้งระบบหรือไม่?

เป็น mAP@50 ของ YOLOv8s บนชุดทดสอบเฉพาะ ไม่ใช่ Accuracy รวมของเว็บหรือระบบแจ้งเตือน

### ระบบตรวจพบการต่อสู้ครบหรือไม่?

ไม่ครบ ใน test 45 คลิป มี Fight จริง 23 คลิป ตรวจถูก 16 และพลาด 7 อีกสองคลิป Non-fight ถูกทำนายเป็น Fight

### no_helmet และ no_vest เป็นคลาสของโมเดลหรือไม่?

ไม่ใช่ ใช้กฎจับคู่ตำแหน่งคนกับหมวก/เสื้อกั๊กที่ตรวจพบ หากตรวจอุปกรณ์พลาดก็อาจประเมิน PPE ผิดได้

### ใช้ ByteTrack แล้วหรือยัง?

โค้ดที่ตรวจพบใช้การจับคู่ด้วย IoU และระยะห่างของจุดกึ่งกลาง เป็น Tracking ระดับทดลอง ยังไม่ใช่ ByteTrack

### เชื่อมกล้องสดได้หรือยัง?

มีเส้นทางรับ RTSP ในโค้ด แต่การตรวจครั้งนี้ยังไม่ได้ยืนยันกับกล้องจริง หากสาธิตด้วยไฟล์ต้องเรียกว่า replay และยังไม่มีหลักฐานรับรอง SLA หรือจำนวนกล้องที่รองรับจริง

### เบลอหน้าแล้วปลอดภัยครบทุกกรณีหรือไม่?

มีส่วนตรวจจับและเบลอใบหน้าด้วย YuNet แต่หากตรวจจับใบหน้าไม่พบก็ยังมีความเสี่ยง จึงไม่รับรองการปกปิดครบทุกใบหน้า

### Dashboard และ Alert Logs เป็นผลจริงหรือไม่?

Dashboard และ Alert / Logs อ่านประวัติจริงจาก SQLite แล้วค่ะ Dashboard นับแถวสรุปผลโมเดลและใช้เวลาบันทึกตาม Bangkok ส่วนสถานะ Live อ่านจาก backend process ปัจจุบัน จำนวนเหล่านี้ยังไม่ใช่จำนวนเหตุที่ยืนยันแล้ว ส่วนโหมดสาธิตใช้ UI ร่วมกัน แต่ข้อมูลในหน่วยความจำมีป้ายผลบันทึก/สมมติแยกชัดเจน

### ชุดทดสอบ API ผ่านแล้วหรือยัง?

ผ่านแล้วค่ะ งาน 1 ทดสอบ snapshot แยกได้ 269 tests หลังรวมงาน 2 ผ่าน 285 tests หลังเพิ่ม Dashboard ผ่าน 287 tests หลังงานแจ้งเหตุสงสัยผ่าน 299 tests และหลังงานค่าตั้งผ่าน 316 tests รวมการย้ายฐานเดิม cooldown persistence และการใช้ค่าจริงในรอบถัดไป ดู [รายงานงาน 1](pipeline-live-verification.md), [งาน 2](history-verification.md), [งาน 3](dashboard-verification.md), [งาน 4](notifications-verification.md) และ [งาน 5](settings-verification.md) ผลนี้ยืนยันการทำงานตามกรณีทดสอบ ส่วนความแม่นยำต้องอ้างผล held-out test แยกกัน

### แต่ละคนทำอะไรในโครงการ?

`[ต้องเติมข้อมูล: ชื่อ งานรับผิดชอบ และหลักฐานผลงานที่สมาชิกยืนยัน]` ไม่อนุมานผู้รับผิดชอบจากชื่อผู้ใช้ในเส้นทางไฟล์

### การแจ้งเตือนลดข้อความซ้ำอย่างไร?

backend บันทึกเมื่อผลปัจจุบันผ่านเกณฑ์และเว้น 30 วินาทีต่อ run/type/model ค่ะ ในการตรวจ Live ด้วยโมเดลจริง พบควันต่อเนื่อง 35 observations แต่แจ้งครั้งเดียวในช่วงพัก เมื่อรับทราบ/ปิดรายการจะหยุดแจ้งซ้ำของแถวเดิมจนเปิดกลับและพบผลเข้าเกณฑ์ใหม่ วิธีนี้ยังไม่ใช่การยืนยันว่าแยกเหตุจริงแต่ละเหตุได้ และยังไม่ส่งออกนอกเว็บ

### หน้าตั้งค่ามีผลกับโมเดลจริงหรือไม่?

มีผลค่ะ ค่าถูกบันทึกใน SQLite และแต่ละคำขอ/Live session อ่าน snapshot ตอนเริ่ม API ส่งค่าที่ใช้จริงพร้อม revision กลับมา ในการตรวจภาพเดิมด้วย YOLOv8n บน CPU ค่าตั้งเดิมพบ Smoke/Fire แต่เมื่อบันทึก threshold เป็น 0.95 ไม่พบกล่องทั้งสองประเภท และหลัง restart ยังใช้ค่าที่บันทึกได้ การเปลี่ยนนี้ยืนยันเส้นทางตั้งค่า ไม่ได้พิสูจน์ว่าความแม่นยำดีขึ้นค่ะ
